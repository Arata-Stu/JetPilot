# フローによる背景補償・調整用第1試行の結果

2026-10-06。ユーザーがLinux側で `analyze_rc_popout_flow.sh` を実行し、
`flow_dev_trial01/summary.csv` とログを提示した。
以下はその出力からの集計であり、こちらで実データを再処理した結果ではない。
主要列の転記：[flow_dev_trial01_reported.csv](evidence/rc_popout_20260930/flow_dev_trial01_reported.csv)。

## 判断

**この設定のフロー方式は採用しない。** EVSは走行中も背景推定がほとんど成立せず、RGBは負例でも多くの候補を出した。
合成テストで確認した処理の整合性と、実データで背景を分離できることは別であり、後者は達成していない。
背景移動補償全般が不可能と示されたわけではないが、閾値を変更して成功扱いへ寄せる段階ではない。

## 観測された値

| 記録 | RGBの走行中判定可能率 | EVSの走行中判定可能率 | EVSの走行中判定可能時間 | RGB候補数（全評価区間） | EVS候補数（全評価区間） |
|---|---:|---:|---:|---:|---:|
| 飛び出しなし | 40.1% | 4.0% | 80 ms | 27 | 0 |
| `test_01` | 59.7% | 1.5% | 30 ms | 14 | 0 |
| `test_05` | 60.3% | 6.0% | 120 ms | 15 | 0 |
| `test_11` | 70.4% | 3.0% | 60 ms | 14 | 0 |
| `test_14` | 53.6% | 4.0% | 80 ms | 10 | 0 |

走行指令区間は約2秒。LED操作を含む全評価区間ではなく、その走行指令区間を分母にした。
判定可能時間は前後両サンプルの背景推定が成立した区間の保守的な集計で、上表の30～120 msが連続しているとは限らない。
EVSの候補0件は、背景推定不能が大半であるため「誤反応を抑えた」と解釈できない。
`status=complete` は処理が完了して有効推定が少なくとも1回あったことを表し、性能の合格判定ではない。

RGBの正例4件の最初の候補は、それぞれ発進指令の5.877、4.320、6.805、2.349秒前。
飛び出しなしでも発進の4.265秒前から候補がある。
従って、誤反応の説明を自車の直進による背景移動だけに限定できない。
人物や別の物体の動き、撮像変動、特徴点の誤対応などは原因候補だが、このCSVだけでは判別していない。

RGB初出現付近の候補数は `test_01 / 11 / 14` が1、`test_05` が0。
多数の出現前候補があり、これを車両検知3/4とは集計しない。

## まだ確定していない原因

保存CSVには背景推定の棄却理由、往復追跡後の対応点数、inlier比率・タイル数・広がりがある。
これを走行中に限定して確認すれば、「対応点不足」「背景モデルへの一致不足」「空間的な広がり不足」を区別できる。
初期特徴点数や往復追跡で落ちた点数は第1試行では保存しておらず、対応点不足の内訳までは復元できない。

10 msのイベント数画像を30 ms離れた画像と追跡する入力表現や、単一アフィン変換の仮定が合わない可能性はある。
ただし棄却理由をまだ受領していないため、それらを原因と確定しない。
現段階では同期・ROI・背景推定条件・候補閾値を変更しない。

## 保存結果だけの診断

新しいレビュー用スクリプトをLinux側へ反映して実行する。標準Pythonのみで動き、ROS、OpenCV、RAW再読取は不要。

```bash
cd /workspaces

bash scripts/experiments/review_rc_popout_flow.sh \
  --flow-dir /workspaces/record/09-30/analysis/flow_dev_trial01 \
  --output /workspaces/record/09-30/analysis/flow_review_trial01 \
  --bundle
```

出力するもの：

- `summary.csv`：全体・発進前・走行中・初出現周辺ごとの判定可能率、最長連続判定可能時間、候補数、背景推定品質の中央値。
- `rejection_reasons.csv`：各区間の棄却理由別サンプル数。処理の最初に該当した棄却理由であり、全制約の独立した寄与分析ではない。
- `candidate_locations.csv`：候補開始時刻のタイル座標。発進前のRGB反応がどこにあるかを確認する。
- `flow_debug_bundle.zip`：元の調整用5件のCSV・メタデータ・タイル配列・保存済み画像と上記診断。RAWと評価用記録は含めない。

保存済みの設定・split・候補時刻・件数との整合を確認し、入力を変更せず新しい出力先へ書く。
元のRAWや現在の同期ファイルを確認したという意味ではない。
端末には走行中の主な棄却理由と最長連続判定可能時間を表示する。
まずその表示を確認し、必要なら生成したZIPで詳細を調べる。

走行中ON時間について、第1試行の出力は区間終点の状態を直前区間へ割り当てる近似だった。
レビューの `active_seconds_causal_hold` は候補が利用可能になった時刻以降へ状態を保持する集計で、値が異なる場合がある。
今後の解析出力もこの集計へ修正した。候補発生時刻・件数・背景推定の判定可能率はこの修正では変わらず、今回の失敗を解消する修正ではない。

## 次の判断

以前の局所変化方式のEVS閾値0.25は、調整用で車両輪郭との対応を確認できた比較基準として残す。
今回のフロー方式は保留し、上の診断で入力表現・対応付け・背景モデルのどこから崩れているかを確認する。
RGBとEVSを共通のルールと評価手順で比べる方針は維持するが、同一の画像追跡器を使うこと自体を成功条件にはしない。
評価用10件と静止記録を追加の調整には使わない。

## 追加提案：活動分布の背景モデルとYOLO

ユーザーから、画素／grid単位のイベント活動分布による分離と、YOLOを使う代案が提案された。
以下は提案時の設計候補。後続でgrid分布方式を実装・実行したため、現時点の結果は
[grid活動分布の背景モデル](rc_popout_grid_background_20261006.md)を参照する。YOLOは実装していない。

現行の局所方式は各タイルの過去中央値・MADと同じ行の中央値を使う。
この提案時点の局所方式は、タイル全体の分布パターンや、タイル間の共変動を背景モデルとして扱っていなかった。
次の候補は、32 pxタイルの活動密度と空間的な比率を併用し、
背景として説明できる広がりから余る局所成分の隣接性・時間的連続性を見る方式。
例えば調整用の飛び出しなし記録から少数の背景パターンを求め、現在までの観測をそれらで説明する。
ニューラルネットワークは不要だが、背景統計を適合する処理なので「学習を一切していない」とは記載しない。
撮影全体の中央値で停止時間の長さに引きずられないよう、背景モデル作成時の走行／停止の重みを明記する。
推論に初出現注釈・未来のサンプル・シーンごとの手動出現位置は使わない。

既存NPZにはタイル別の活動数があり、この分布パターンの予備検証はRAW再読取なしで可能。
ただしタイル内の画素分布・イベント極性・正確なイベント時刻列は保存されていない。
背景も局所的に反応するため、活動分布だけで対象を常に分離できる保証はない。
調整用負例は1記録であり、それに合わせた0件を一般化性能とは扱わない。

YOLOは通常のRGB画像や3チャンネル配列を入力できる
（[Ultralytics公式入力仕様](https://docs.ultralytics.com/modes/predict/)）。
イベント数・極性等を3チャンネル画像に変換することもできるが、RGB用の学習済み重みが
その表現上のRCカーを認識できることは未検証。画像形式の一致は入力分布や学習条件の一致ではない。
[E2VID公式実装](https://github.com/uzh-rpg/rpg_e2vid)にはイベントから輝度画像を復元する選択肢もある。
この構成でYOLOを使う場合、画像復元モデル・蓄積窓・復元処理時間も比較対象へ含める必要がある。
単色イベントから3チャンネルを作ることを、実測RGBの色復元と説明しない。

優先案は既存のEVS局所候補を比較基準として保持し、同じ調整用でgrid分布の予備検証を行うこと。
RGB用YOLOを実用的な参照手法として追加する選択肢もある。
RGB-YOLOとEVSルール方式を比較するなら、結論はセンサと検知方式を合わせたシステムの比較とし、
センサ固有の優劣だけへ帰属させない。同一YOLOの採用だけでは、この制約は解消されない。
