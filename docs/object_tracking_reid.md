# 物体追跡と周回をまたぐReID

追記: 独立したC++ ReIDノードの実装を追加しました。画像バッファ・ROI前処理・TensorRT推論・
外観ギャラリー・ID対応の出力については [ReID実行ガイド](reid_runtime.md) を参照してください。
以下の検討には将来の学習・位置情報融合・レース分析の設計も含まれます。モデル自体は未同梱です。

## 導入した追跡機能

YOLOv8 decoderのNMS後に、標準C++だけで動くByteTrack風Trackerを追加しました。
TensorRT engineの再生成やUltralyticsの実機インストールは不要です。
`/perception/detections`の型は変更せず、追跡確定後の`Detection2D.id`に
`起動セッション識別子:追跡番号`を設定します。ID未確定の検出も従来どおり出力し、idは空です。
既存のbag記録設定でIDも保存され、Bag Analysisは`track_id`を保持し、動画に番号を表示します。
古いbagにはIDがないため、追跡付きのオフライン推論を再実行する必要があります。

処理は高信頼度boxとのクラス別IoU対応付け、未対応の追跡と低信頼度boxの再対応付けの2段階です。
割り当てはHungarian法、位置予測は撮影時刻に基づく平滑化した等速予測です。
ByteTrack論文のKalman filterや全ライフサイクルを再現した実装ではありません。
カメラ移動補償、外観特徴、Map位置による対応付けは今回含みません。

`config/yolov8.param.yaml`の起動時設定:

| 設定 | 初期値 | 意味 |
|---|---:|---|
| enable_tracking | true | ID付与を有効にする |
| confidence_threshold | 0.35 | 高信頼度対応付けと従来の検出出力の閾値 |
| tracking_low_score | 0.10 | 追跡維持にだけ使う低信頼度boxの下限 |
| tracking_new_score | 0.50 | 新規追跡を作る下限（高信頼度閾値以上） |
| tracking_match_iou | 0.30 | 予測boxと検出boxの最低重なり率 |
| tracking_lost_seconds | 0.5 | 最後の観測から追跡を保持する秒数 |
| tracking_min_hits | 2 | ID確定に必要な対応付け済み観測数 |

低信頼度boxだけで新しいIDは作りません。低信頼度boxは、直前まで見えていた確定済み追跡を
補うために使い、見失い状態からの復帰には高信頼度boxを要求します。
出力閾値未満のboxと、見失い中の予測boxは`/perception/detections`へ出しません。
このため、動画表示から一時的にboxが消えても内部IDが維持される場合があります。

保持期限を超えると再遭遇は新しいIDです。時刻巻き戻しやframe_id変更では追跡状態を破棄し、
同じプロセス内で番号は再利用しません。再起動後は別セッションのIDになります。
メモリ・対応付け負荷を制限するため、内部追跡数は最大128です。
現在の設定を変更するときはdecoder設定ファイルを編集して再起動してください。
信号用設定では追跡を無効にしています。

## ReIDの実装可能性

実装可能ですが、現在の`model.onnx`の出力はbox/classだけです。外観特徴が含まれないため、
この出力だけで「前の周回に見た車両」との照合はできません。
TensorRTで動かす小型の外観特徴抽出器を別途追加する構成を推奨します。

```text
RGB → YOLOv8 → 短期Tracker → track_id
 │                           │
 └→ 撮影時刻で同期した車両crop → 外観特徴抽出 → 個体履歴との照合
                                              └→ opponent_id / 確信度 / 不明
```

1. **画像同期**: 元RGBを短時間だけ保持し、検出のheader timestampと同じ画像からboxを切り出す。
   最新画像で代用すると、走行中には別の領域を切り出す危険があります。
2. **特徴抽出**: 224入力へ縮小した画像でなく元画像のcropを使う。
   小さすぎる・ブレた・強く隠れたcropは履歴更新に使わない。
   `vehicle`だけを対象にし、毎フレームでなく品質の良い観測を間引いて処理する。
3. **個体履歴**: レース単位の`opponent_id`に、複数の向きの特徴、代表画像、最終観測時刻、
   過去のtrack_idを紐付ける。永続化先はレースIDとモデル版で分離する。
4. **照合**: 特徴の類似度、1位と2位候補の差、複数観測の一致で復帰を判断する。
   不確かなときは`unknown`とし、過去のIDへ強制統合しない。
5. **公開方法**: `Detection2D.id`は短期track_idのまま維持し、ReIDの個体IDとの対応を別messageで
   配信・保存する。後から照合を訂正しても、元の追跡履歴は変更しない。

独立した特徴抽出器を呼び出すC++ノード・個体gallery・ReIDのROS messageは実装済みです。
学習済みモデルの用意、位置情報との融合、実車での精度評価は今後の作業です。

## 用意すべきデータと評価

必要なのは車両クラスのboxラベルに加え、「どの個体か」が分かるラベルです。
同じ相手の前・後・側面、近距離・遠距離、照明違い、複数周回を収集します。
色が似た別車両も必ず含め、評価用の走行セッションを学習から分離します。
Trackerが自動生成したIDを、そのままReID学習の正解にしないでください。
一般の実車・歩行者向けモデルがRC車両にも有効かは未確認で、実データ評価が必要です。

短期追跡はID切替回数・断片化・IDF1/HOTA、長期再識別は「別車両への誤統合率」と
再遭遇時の正しい復帰率、unknown率を測ります。周回再遭遇の正解一覧を作ると比較できます。
TensorRT化後にcuVSLAMと同時実行し、遅延・GPUメモリ・温度を測ってから頻度とモデルを決めます。
今回のTrackerも、実bag/Jetsonでの交差・急旋回・遮蔽に対する精度と処理時間は未検証です。

Map/TFは自車の動きの補助に使えますが、2D boxから相手の3D位置は直接求まりません。
路面への投影や深度を導入する場合も、位置の不確かさを含めて照合します。
周回をまたぐ長い消失を、画像上の等速予測だけでつなぐことは想定しません。

## 次の実装順序

まず今回のTrackerでbagを再解析し、ID切替を評価します。その後、保存済みcropによる
オフラインReIDの比較試験を行い、RC車両に適した特徴抽出器・閾値を決めます。
有効性を確認してから、TensorRT特徴抽出とレース単位の履歴管理をROSに組み込みます。

参考: [ByteTrack原論文](https://arxiv.org/abs/2110.06864)、
[BoT-SORT原論文](https://arxiv.org/abs/2206.14651)。
前者の低信頼度boxの活用を今回取り入れ、後者の外観情報・カメラ移動補償は今後の比較対象です。

## 相手ごとの走行特性を追い越しへ利用する設計案

目的は、相手の識別を継続して、コース位置ごとの速度・走行位置を学習し、再遭遇時の
追い越し候補評価に使うことです。3台レースが自車込みなら相手2台ですが、相手数を2に固定せず
未知の車両も扱う可変長の状態配列にします。以下は設計案であり、実装済み機能ではありません。

### 認識から状態推定

外部カメラから得るのは相手自身の車輪odometryではなく、観測に基づく位置・速度の推定です。
画像上のbox移動には自車の移動が混ざるため、自車pose、撮影時刻のTF、距離推定を組み合わせます。
現行RealSense launchはdepthとRGBへのdepth alignmentが無効です。
距離取得は、RGBと対応付けたdepthまたは既知路面への接地点投影を比較評価します。
box中央のdepthには背景が混入し、box下端の路面投影には遮蔽・車体形状による誤差があるため、
どちらも単一画素をそのまま相手の車軸中心として扱わない設計が必要です。
D455での路面・車体に対するdepthの有効性、遅延、cuVSLAMへの負荷は実機評価事項です。

状態推定は`track_id`ごとに連続なローカル座標で行い、Mapへの変換でコース位置を求めます。
自車の再localizationによるmap→odomの跳びを相手の加速と誤認しないよう、変換の不連続時は
特性更新を止め、再初期化または座標補正を行います。
速度ベクトルの向きと車体の向きは別であり、停止中や横滑り中の姿勢を速度から確定しません。

### 状態と個体メモの分離

| データ | 保存する情報 | 有効期間 |
|---|---|---|
| 現在状態 | track_id、観測時刻、位置・速度と共分散、可視状態、車体寸法の推定 | 短時間、失効あり |
| 個体対応 | opponent_id、ReID確信度、対応候補、訂正履歴 | レース単位 |
| 走行メモ | コース位置ごとの速度・横位置の平均/分散、観測数、更新時刻、状況 | レースとMap版で分離 |

ReIDが未確定でも現在の障害物として扱います。確信度が低い観測で既存個体のメモを更新しません。
元観測とtrack_idは保存し、誤対応が判明したら集計をやり直せる構成にします。
見失った間は位置の不確かさを増やし、長期の個体メモを「今そこにいる」という証拠にしません。
前方カメラで見えない区間の相手軌跡は観測済みとして記録できません。

### コース位置での集計

centerlineに沿う距離`s`と横ずれ`d`に変換し、距離区間ごとに特性を蓄積します。
Sectionは表示用のまとまりに使い、1 Sectionコースでも動作させます。
周回境界はコース長での折り返しを考慮します。長い消失後の周回数は不確かなまま保持します。
交差・分岐では最近傍点だけでなく以前の進行方向とlane候補を使い、曖昧なら更新しません。

最初のメモは「この位置での速度」「内側/外側への偏り」「観測のばらつき」で十分です。
観測数と最終更新時刻を添え、古いデータの重みを落とします。
単独走行・他車追従・並走中を可能な範囲で区別し、状況依存の減速を車両固有の弱点と混同しません。
高度な学習モデルの前に、オンラインの区間統計を基準方式として評価します。

### 予測と経路提案

短期の運動予測に、過去の速度・横位置傾向を事前情報として加えます。
未来は一本の線ではなく、位置の不確かさと複数の動作候補を含めて扱います。
自車が接近すると相手の行動も変わり得るため、履歴の平均経路を確定的に外挿しません。

候補は追従・内側通過・外側通過・次の区間まで待機から始めます。
相手全台の将来占有領域、壁と車幅、合流地点、操舵/加減速限界、情報の古さを評価します。
衝突・境界制約を満たす候補の中で、進行量、追い越し所要時間、制御の滑らかさを比較します。
一台を抜いた先で別の一台に塞がれるケースも評価対象です。

`jetpilot_planning`には外部候補Path/Trajectoryとlane要求を受ける仕組みがありますが、
時空間の衝突判定・追い越し軌道生成は未実装です。専用の候補生成器を追加し、
`jetpilot_planning_manager`の調停へ統合します。同じ最終topicへ別publisherから直接書きません。
既存の信号・復帰との優先順位も定義し、動的候補には失効時間と要求のheartbeatを設定します。

### 段階的な実装・評価

1. bagで相手の位置・速度推定を検証し、UIに軌跡と不確かさを表示する。
2. ReIDを接続し、個体別・距離区間別の走行メモを保存する。
3. bag再生で追従/内側/外側の候補と理由を表示し、制御には接続しない比較評価を行う。
4. シミュレーションと実車の段階評価で、複数相手・再遭遇・誤ReID・位置欠損を検証する。
5. 有効性を確認した候補生成をplanning managerへ統合する。

関連研究として、相手軌跡の予測を追い越しに使う
[Predictive Spliner](https://arxiv.org/abs/2410.04868)と、複数相手の追跡・再対応付けと
位置/速度予測を組み合わせる[M-Predictive Spliner](https://arxiv.org/abs/2506.16301)があります。
1/10スケールの実験例は今回の構成検討に近い一方、センサーと環境が異なるため、論文中の性能を
このRGB主体のシステムにそのまま期待するものではありません。
