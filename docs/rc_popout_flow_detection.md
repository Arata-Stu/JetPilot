# RGB・EVS共通の背景移動補償による局所候補（調整用）

2026-10-06に実装した試作。撮影済みの調整用5件からRGB画像とRAWイベントを読み直し、
背景の動きで説明できない特徴点の集まりを抽出する。ニューラルネットワークや学習済み重みは使わない。
実データの第1試行ではEVSの走行中判定可能率が約1.5～6.0%にとどまり、RGBも負例で27候補となった。
この設定は採用せず、[第1試行の結果と保存結果だけの診断](rc_popout_flow_trial01_review.md)へ進む。

既存EVS閾値0.25の[画像照合結果](rc_popout_candidate_visual_review_20261006.md)は比較基準として残す。
この試作ではEVS入力を過去10 ms窓・10 ms更新の画像へ変えるため、従来の過去2 ms窓・1 ms更新の方式と区別する。

## 実行

新規ファイルと、画像／イベント受け渡しを追加した `tools/rc_popout_detection.py` をLinux側へ反映する。
既存と同じ校正用Python環境、ROS bag読取環境、Metavision SDK、NumPy、OpenCVが必要。
ROSノードの起動や車両の接続は不要。MP4や局所タイルNPZだけからは実行しない。

```bash
cd /workspaces

bash scripts/experiments/analyze_rc_popout_flow.sh \
  --motion-dir /workspaces/record/09-30/analysis/detection_motion_trial01 \
  --subset development \
  --output /workspaces/record/09-30/analysis/flow_dev_trial01

cat /workspaces/record/09-30/analysis/flow_dev_trial01/summary.csv
```

対象は固定済みの `t_0.2-none`, `test_01`, `test_05`, `test_11`, `test_14`。
先に入力の存在とハッシュだけ確認する場合は同じコマンドへ `--dry-run` を加える。
dry-runでは出力先を作成しない。RAW復号・有効画素・時刻範囲の検査は本実行時に行う。
既存出力は上書きせず停止する。再試行は `flow_dev_trial02` など新しい出力先を指定する。
`--subset evaluation` は受け付けない。

イベント画像は時刻ビンごとの一時ファイルを作り、RAWのEOFまで読んでから順に処理する。
640×480、2倍縮小、10 ms更新なら評価区間20秒で約586 MiB。記録ごとに解放する。
必要量を事前表示し、既定の2,048 MiBまたはディスク残量を超える場合は停止する。
必要な場合だけ `--max-cache-mb` を増やす。一時ファイルは正常終了・通常の例外時に削除する。
強制終了で残った `.event_frames_*` は再開用キャッシュではない。

## 同じ判定構成

RGBは歪み補正・EVS座標への投影後のグレースケール画像、EVSは同じROIのイベント数画像を入力する。
EVSでは両極性を数え、縮小後の画素ごとに3イベントで飽和する固定変換を使う。
画像ごとの最大値・未来の分布による正規化は行わない。
両者を2倍縮小し、同じ小さな平滑化を施す。

1. 32×32の元画像座標タイルごとに最大6特徴点を選ぶ。床の高密度テクスチャだけで推定が占有されることを抑える。
2. 現在から少なくとも30 ms前の画像との間で、ピラミッドLucas–Kanade法による対応を求める。逆方向にも追跡し、往復誤差が大きい点は除く。
3. RANSACで支配的な背景のアフィン変換を推定する。平行移動・拡大・回転・せん断を表す2次元近似である。
4. 背景モデルが予測する位置と実際の対応位置の差を、元画像の画素単位で求める。
5. 大きな残差を持つ点が2点以上、かつ対応点の半数以上を占めるタイルを選ぶ。上下または左右に隣接する2タイルが20 msにわたり条件を満たすと候補にする。

処理にはOpenCVの公式API
[calcOpticalFlowPyrLK](https://docs.opencv.org/4.x/dc/d6b/group__video__track.html)と
[estimateAffine2D](https://docs.opencv.org/4.x/d9/d0c/group__calib3d.html)を使う。
背景の推定も候補の判定もセンサーごとに独立し、RGBの動き推定をEVSへ渡すことはしない。
発進・飛び出し方向・初出現注釈は検知器へ渡さない。

## 初期設定と時間の意味

| 項目 | 初期設定 |
|---|---|
| EVS画像 | 過去10 ms、10 ms更新（100 Hz）、両極性の個数 |
| RGB画像 | 実際に記録されたフレームごと。補間・フレーム複製なし |
| 参照画像 | 30 ms以上前の最新画像、最大70 ms前まで |
| 背景推定 | 24点以上のinlier、inlier比率0.55以上、8タイル以上に分布 |
| 背景の広がり | ROIの横幅35%以上・縦幅20%以上 |
| 対応点の残差閾値 | max(2 px, 40 px/s ×画像間隔, 背景残差中央値＋4×MAD尺度) |
| MAD尺度 | 1.4826×MAD、下限0.25 px |
| 候補 | 隣接2タイル、各2点以上・50%以上、20 ms持続 |
| 欠測によるリセット | 画像間隔100 ms超、評価区間境界 |

同じ数値を両センサーに適用する初期試作であり、実データで最適化した設定ではない。
画像間隔や持続条件は時間で定義し、候補時刻を過去へ繰り上げない。
持続は同一タイルペアの観測に対して数え、別の場所の反応を足し合わせない。
全体の候補開始だけでなく、全体反応中に始まった別ペアも `*_pair_starts.json` へ残す。

EVSの現在画像は `[t−10 ms, t)`。参照画像の終端は現在窓の開始以前で、未来のイベントを含まない。
RAWのバッチ順序が乱れていても、時刻ビンに加算して重複イベントを保存する。
これはイベント時刻に対する因果的なオフライン処理であり、実際の到着遅れやオンライン計算時間は測っていない。

新しく現れた対象は、追跡可能な特徴が過去画像にも存在するまで拾いにくい。
参照間隔と持続条件自体が候補を遅らせるため、EVSの素子応答速度をこの結果から測定したとはしない。
既存の2 ms活動量方式より速くなることを前提にしない。

## 判定不能の扱い

特徴不足、背景inlier不足、空間的な偏り、過大な拡大縮小などではスコアを欠測にし、候補の持続状態をリセットする。
その区間をスコア0や正しい非検知として扱わない。
ROIの人工的な黒い境界を追跡しないよう、LK窓の半幅分だけ内側にある特徴点を使用する。
そのため、視野端へ入った直後の対象を検知しにくい制約もある。

単一アフィン変換では、床・壁・遮蔽物の奥行き差による背景の動き全ては表現できない。
移動物体が対応点の大半を占める場合も、背景モデルとして正しく推定できる保証はない。
静止条件のEVSでは背景イベントが少なく、そもそも背景推定が成立しない可能性がある。
両条件へそのまま適用できる最終手法と決めたわけではなく、これらの失敗理由も記録して判断する。
センサー間の `rotation-only` 投影による位置ずれを、このセンサー内の背景補償が解消するわけではない。

## 出力と最初の確認

`index.html` に各センサーの波形と確認画像を掲載する。

| ファイル／項目 | 意味 |
|---|---|
| `summary.csv` | 候補数・時刻、判定可能な時間、走行中の判定可能率と反応時間 |
| `drive_ready_fraction` | 記録された走行指令区間に対し背景推定が成立した時間の割合。LED操作による待ち時間と分ける |
| `drive_active_seconds` | 走行指令区間の候補ON時間の離散近似 |
| `*_phases.json` | 走行前・走行・制動の各区間での候補と判定可能時間 |
| `*_flow_scores.csv` | 全時刻の背景推定品質、残差、ペアスコア、状態、判定不能の理由 |
| `*_flow_tiles.npz` | タイルごとの追跡点数・残差点数。`ready=False`行のゼロ配列は欠測の格納値 |
| `*_candidates.json` | 全体候補の開始時刻と、その時点で成立したペアID |
| `*_pair_starts.json` | ペアごとの持続条件成立時刻。全体候補中の別ペアも含む |
| `*_first_candidate.png` | 最初の候補時刻の背景点・残差点と、持続条件成立中の枠 |
| `*_peak_score.png` | 全保存区間で最大スコアになった時刻。注釈時刻で画像を選ばない |
| `result.json` | 調整条件・入力ハッシュ・失敗理由別件数・表示画像時刻 |
| `detector_parameters.json` | この試行の設定の保存。評価用への固定宣言ではない |

候補がない場合は `first_candidate.png` を生成しない。背景推定が一度も成立しなければ
`status=unobservable` として非ゼロ終了し、結果自体は保存する。
`candidates=0` だけで良否を判断せず、まず走行中の判定可能率と `result.json` の `status_counts` を見る。
有効観測時間は、前後両サンプルで背景推定が成立した時間だけを保守的に加算する。

画像の緑点は背景モデルのinlier、赤点と線は大きい残差、灰色点はその中間、橙枠は持続条件を満たしたペア。
RGB画像とEVS画像はそれぞれ自身の動き判定結果を描く。
CSVのアフィン行列は縮小画像座標、残差のpx値とタイル座標は元のEVS画像座標。

まず `summary.csv` と、最初の候補／最大スコアの画像を確認する。
候補数にかかわらず、`first_candidate_minus_onset_ms` はRGB手動初出現注釈との差であり、RGB検知器との差ではない。
前30 ms／後250 msの集計は診断用で、候補を発生させる条件には使わない。

## 検証と今後

合成画像・対応点で背景の平行移動と拡大、独立移動領域の残差、特徴不足、ペアごとの持続、
未来画像による過去結果の不変、区間／欠測リセット、順不同・重複イベントと因果窓を確認した。
模擬入力によるCLI実行、調整用だけの読取、既存出力の保護、一時ファイルの削除も確認した。
既存抽出器への観測コールバックの追加によってRGB/EVSの元スコアが変わらない回帰テストを含め、27テストが通過。
合成画像の確認PNGも目視した。実際のROS bag／Metavision RAWをこの環境で再処理した結果ではない。

```bash
python3 -m unittest discover -s tests -p 'test_rc_popout_flow.py' -v
python3 -m unittest discover -s tests -p 'test_rc_popout_detection.py' -v
python3 -m unittest discover -s tests -p 'test_rc_popout_tile_activity.py' -v

```
