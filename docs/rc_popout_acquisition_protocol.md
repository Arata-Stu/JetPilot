# 飛び出しブレーキ研究：収録仕様と撮影手順

作成日: 2026-09-26

状態: 必須保存項目、自車静止、飛び出し車のプロポ上限設定＋フルトリガ操作を確定。具体的な上限値、現場寸法、試行数、今回の人間実験実施有無は未確定。

## 1. 今回の目的

同期したRGB・EVSの元記録から、後日、軽量検知器の仮想ブレーキ要求成立時刻差、誤要求、見逃しを評価する。人間には同じ試行のRGB映像を提示し、G923のペダル応答を別途測定する。

本仕様は、既存のROS 2ドライバ・オンライン実機評価ロードマップを置き換えない。オンライン定性実演は後段で行える。過去の受信時刻、処理遅延、実制動性能は、今回測定していなければ後から復元できない。

## 2. シナリオ撮影で必ず保存するもの

| 必須項目 | 保存内容 | 欠けた場合の影響 |
| --- | --- | --- |
| RGB元画像と時刻 | 元解像度・元フレームのbag、各画像header、bag記録時刻、camera_info、取得可能なフレームmetadata | MP4のみでは元フレームと時刻の対応が失われ得る |
| EVS元イベント | native RAWと隣接する`*.raw.metadata.yaml`。デコード時の時刻原点・time shift設定も保存 | 表示用イベント動画からイベント単位の評価は復元できない |
| bag管理情報 | 全MCAP分割ファイルとbagの`metadata.yaml`を含むセッションディレクトリ全体 | 一部ファイルだけでは記録が不完全になる |
| セッションごとの光学同期 | 同じ収録内の開始・終了LEDパターンをRGB・EVS双方へ記録。パターン仕様・firmware版も保持 | 記録固有の時計差・ドリフトを評価できない |
| 空間校正の対応 | 使用したcamchain・profileのコピー、校正ID、カメラ取付状態の写真 | どの校正が適用可能か不明になる |
| センサ設定 | 型番・識別子、解像度/FPS、露光・gain・自動露光設定、EVS bias・フィルタ設定、SDK/driver版、起動設定 | 条件依存性や前処理によるイベント除去を追跡できない |
| 試行識別と配置 | session_id、trial_id、元ファイル、試行順、配置ID、予定条件と実際の実施内容 | 動画と実験条件を対応付けられない |
| 配置の実測記録 | 自車走行領域、車幅、遮蔽物・開始位置・相手車経路、距離、カメラ高さ、単位付き配置図・写真 | 実空間の危険領域や距離条件を再設定できない |
| 記録品質 | センサdiagnostics、警告、記録開始終了、再起動、欠落・中断のメモ | 欠損を無反応や低遅延と誤解する可能性がある |

露光などのフレームごとの値が機器から取得できない場合は、設定値と「実測値なし」を残す。設定FPSを実測FPSと扱わない。時刻の単位・時計ID・意味が不明なら不明として残し、ゼロなどで代用しない。

走行する場合は、自車の操作・制御指令と動作モードを保存する。相手車の指令も取得できるなら保存し、取得できない場合は操作者・指令設定・発進と停止の手順を記録する。スロットル率は速度の実測値ではない。実速度別の分析を予定する場合は、スケールを実測した走行区間を外部固定カメラ等で記録するか、時刻付き速度計測を追加する。

第三視点動画は今回の要求時刻差には必須ではないが、全体配置、相手車の経路、停止、操作者の介入の確認に有用。センサと時間対応させる場合は同じLED等の共通事象を写し、精度も別に評価する。物理的出現時刻の高精度な正解と自動的に扱わない。

## 3. 現行プロジェクトとの対応

- `scripts/bringup.sh rc-popout`はRGB 848×480・60 Hz、EVS native RAWの設定を選択する。
- 使用する`bag_manager.rgb_evs_benchmark.param.yaml`にはRGB画像・metadata・camera_info、EVS camera_info・diagnostics、RAW開始要求、車両制御関連トピックが列挙されている。
- トピックの列挙は実際のpublish・記録を保証しない。車両系は起動していなければ入らない。
- 通常のbag設定と専用設定を混同しない。専用設定にはRAW連携先が指定されているが、必ず試し撮りでRAWの実生成を確認する。
- 既定校正は`ros2_ws/src/tool/multi_sensor_calibration/config/calibrations/rc_popout_default/`。空間校正は取付・光学系・画像条件が同一の場合に再利用する。時間同期値はセッションごとに確認する。
- `rc_popout_evs_rgb.yaml`は暫定時間軸にbag時刻を選ぶ。これは露光時刻・ホスト受信コールバック時刻を意味しない。元headerとmetadataを保持し、後処理で時間軸の意味を監査する。
- 校正設定のマス寸法は25 mmだが、設定コメントに暫定値との記述が残っている。実物のマス寸法を実測し、使用した校正の根拠と一致するか確認する。違う場合は実測値と元校正記録を保持して再計算する。
- 現行の試行作成スクリプトは方向・スロットル等の条件表を作るが、本仕様の危険なし条件、役割分割、評価区間を自動で満たすものではない。収録台帳へ明示する。

## 4. シナリオ採用案

### 主条件

自車と搭載RGB・EVSを静止させ、一人で撮影する。一つの照明・遮蔽物配置・相手車スロットル条件から始める案とし、左右の出現を用意して、試行数を増やす前に正常に収録できることを確認する。

主評価は「静止した自車の視点で、相手車が遮蔽物から横方向へ現れ、自車の指定進路へ侵入する」条件とする。測るのは指定進路への侵入に対する仮想ブレーキ要求であり、自車運動への耐性や実走行中の衝突回避性能は別段階で評価する。

飛び出し車はプロポでアクセル最大出力を％設定し、各試行の発進時にトリガをフルまで操作して、走行区間中は保持する。停止時はトリガを戻す等、実車に合う停止操作を行う。開始位置・向き・遮蔽物端までの助走距離を床の印で固定し、同じ区間での操舵操作も揃える。出現前からフルトリガを保持できる助走距離を予備撮影で確認するが、定速になったとは仮定しない。

プロポ型番、使用した機能名（EPA等、実機の表示をそのまま記録）、上限％、設定画面の写真、スロットルカーブ・トリム・走行モード、車両/バッテリーIDと交換タイミングを保存する。上限％は速度ではなくプロポ設定値として扱う。同じ上限値・フルトリガでも実速度の一致は保証しない。ROSへ入らないプロポ操作はbagで自動記録されると考えず、台帳に残す。操作開始時刻を正解出現時刻とせず、出現・侵入はセンサ記録から注釈する。

危険領域は撮影前に、自車幅と固定の余裕幅に基づく床面領域として定義する。数値と配置写真を残す。後から対象に合わせて領域を動かさない。

| 条件 | 再現する動作 | 必要性 |
| --- | --- | --- |
| H-L | 左から出現して進路へ侵入 | 危険あり |
| H-R | 右から出現して進路へ侵入 | 危険あり |
| N | 自車静止のまま相手車の出現なし | センサノイズ・背景変化への誤要求 |

今回の最小構成は上記3条件。進路外の動き（M-L/M-R）は将来追加する条件であり、初回には含めない。自車直進は、まず飛び出しなしで背景運動への誤要求を確認してから左右飛び出しへ進む。

非侵入条件は、危険条件と同じ接近軌道から最後に急停止するだけの動作にしない。それ以前のブレーキが妥当な可能性があるためである。最初から進路外を平行移動するなど、映像上で区別可能な経路を選ぶ。なお曖昧なら`unknown`として保持する。

危険条件の相手車は進路へ侵入後、規定位置で停止する案を基本とするが、停止/通過は予備撮影で確定する。横断して通過する既存記録は通過条件として区別し、停止条件へ読み替えない。操作者の停止・修正操作を残し、停止による映像変化を検知の手掛かりに含めないよう、評価可能区間を後から注釈する。

### 試行数と分割の案

初回は3条件×各6試行＝18試行を収録枠の案とする。各条件2試行を設定用、4試行を評価用として事前に割り当てる。試行数と上限値は未確定であり、撮影支援の既定反復数は3回（動作確認用）である。これは着手用の予備評価案であり、統計的な十分性を保証する試行数ではない。撮影日・条件をまたぐ一般化の主張には別条件の評価を追加する。

予備撮影は別IDで保存し、本評価数へ混ぜない。条件を交ぜた撮影順を作り、実際の順序と撮り直しを残す。同じ連続記録由来の切り出しは同じ分割に置く。人間実験の参加者数はこの物理試行数とは別に設計する。

## 5. 各記録の手順

初回は1記録1試行を基本とし、次の順で行う。

1. 台帳にID・配置・予定条件・設定用/評価用を記入する。
2. 両センサの記録を開始し、ファイル生成を確認する。
3. 両カメラから見える位置で、静止したLED板の開始パターンを最後まで記録する。
4. LED板を取り除き、手や板の動きがなくなってから1秒以上の除外区間を置く。
5. 自車は静止を維持し、相手車の開始位置・向きとプロポの上限設定を確認する。
6. 目安として出現前4秒以上、出現後2秒以上を確保する。相手車の走行・停止が収録範囲に収まるか予備撮影で確認し、不足は台帳へ残す。
7. 相手車をフルトリガで規定経路へ発進させる。発進の待ち時間は試行間で変え、危険なし条件も同等の観測時間を収録する。実際の出現・侵入時刻は後から付与する。
8. 試行終了後に両車を停止し、LED板を静止させて終了パターンを記録する。
9. 正常に収録を終了し、ファイルを確認する。実際の条件、失敗・介入・中断を台帳へ追記する。

複数試行を一つの連続記録に入れる場合は、開始・終了LED、各試行の識別・区間対応、時計リセットがないことを確保する。途中の再起動・再接続は別セッションとして同期を取り直す。

人間提示用の重畳なし映像は元RGBから後で作る。LED、検知枠、要求表示、操作者の声などを提示刺激に含めない。危険条件だけ短いなど、長さから答えが分かる収録を避ける。

## 6. 最初の試し撮りで確認する合格条件

- MCAP、bagのmetadata、RAW、RAW sidecarが存在し、ファイルサイズが増え、正常終了後に読める。
- RGBの最初・中間・最後の画像が読み出せ、EVSも同区間をデコードできる。ファイルの存在だけで合格にしない。
- 開始・終了のLEDパターンが双方に写り、対応付けできる。片側だけなら撮影中に修正する。
- RGBのフレーム間隔、EVS時刻の連続性、diagnosticsから大きな欠落や時計リセットの有無を確認する。
- LED同期の暫定推定を1本で実施する。失敗や不明な周期対応を残したまま大量撮影へ進まない。許容精度は主張したい時間差に照らして決める。
- 対象の出現前・侵入・その後が双方の視野にあり、露光・飽和・遮蔽により確認不能になっていない。
- カメラ間の位置関係と校正条件が維持されている。校正寸法の実測根拠がある。
- 試行IDとファイル対応が一意である。危険なし条件も記録する。
- 別媒体へコピーし、チェックサム一致を確認してから元記録の削除を検討する。

上記は収録機または解析環境で行う現地確認。macOS上で依存パッケージを追加・実行することを本仕様は要求しない。

## 7. G923人間実験を実施する時点で必須の記録

人間実験が後日なら、今回のシナリオ撮影時にG923を同時収録する必要はない。後日の実験では次を保存する。

- 匿名参加者ID、trial_id、元recording_id、クリップと元フレームの対応、試行順、練習/本試行。
- 表示予定時刻、ソフトウェアから取得可能な画面更新時刻、そのAPI上の意味、提示フレームID、フレーム落ち。入力記録と共通の単調時計を使用する。
- ブレーキとアクセルの入力値の時系列、各入力の取得時刻、取得方式（変化通知/定周期読み取り）、更新間隔、接続断や読み取り失敗。閾値越えの1時刻だけにしない。
- G923の型番/識別子、OS・入力API・ソフトウェア版、軸の割当・方向・範囲、感度・dead zone、実験前後の未踏/踏み込み校正。
- 足の初期位置、踏み替えの有無、教示文、椅子・ペダル配置、モニタ型番・リフレッシュレート・提示条件。
- ペダル応答閾値と設定版、試行前から踏んでいた状態、早押し、無応答、接続断、除外理由。

閾値は予備実験で決め、本評価では固定する。生の軸時系列を残すことで事前定義した感度分析は後から可能。入力値は実測踏力ではなく正規化前の機器入力値も保持する。描画完了を物理的発光時刻、入力取得を機械的踏み始め時刻と同一視しない。物理的表示・入力遅延を補正して主張するなら、その計測も人間実験時に行う。

## 8. 後から作れるもの／作れないもの

後から作れる: ROI、試行区間、出現/侵入注釈、同期推定、イベント窓、検知スコア、仮想要求、オフライン集計、提示用クリップ。ただし元情報・対応関係が保存されていることが条件。

後から作れない: 未収録イベント/フレーム、写っていないLED、記録していない取付変更や実測寸法、その実行時の受信・処理遅延、実測していない人間応答や停止距離。

将来、今回の走行自体をROS 2オンライン定量評価にも使うなら、センサバッファ/フレームIDに対応するホスト受信時刻、元バッファ境界、処理開始終了、要求生成時刻、時計の対応を今回から追加する必要がある。RAWのアンカーやbag保存時刻だけでは代用できない。今回これらを追加しない場合、オンライン評価は後日の新規実行で行う。

## 9. 現場で確定する値

- 自車静止とプロポ上限設定＋フルトリガ操作は確定済み。
- 実測配置: 車幅、進路余裕幅、遮蔽物、自車/相手車の開始・停止位置、カメラ高さ。
- 相手車: プロポの機能名・上限％、助走距離、侵入後停止/通過、非侵入経路。
- 前後の収録時間: 人間提示用の切り出し余裕と走行距離の両方を満たす値。
- 撮影枠: 提案18試行を実施可能か。既存記録は内容・品質を監査して不足分へ充当する。
- 人間実験: 今回実施か後日か。今回なら実験用PC・OS・G923読取と提示ログの予備確認。

これらが未確定でも保存項目は準備できるが、最終撮影条件が確定したとは扱わない。

## 10. 現在使える撮影支援・解析入口

収録機のROS環境で、まずセンサを起動する。

```bash
bash scripts/bringup.sh rc-popout
```

別ターミナルで撮影を進める。自車は静止し、シェルは相手車を制御しない。

```bash
bash scripts/experiments/rc_popout_experiment.sh --experiment-dir /workspaces/record/rc_popout_static
```

初回は配置・プロポ上限・反復数を入力する。表示される寸法や上限は入力例であり、現場で確認した値へ変更する。条件の既定値は`left,right,none`。`none`は上限設定数にかかわらず配置・照明ごとに指定反復数だけ生成し、throttleは`na`とする。既存の試行表は自動変更しない。別の実験ディレクトリを使うか、バックアップを作る`--new`を明示する。

`plan.tsv`、`completed.txt`、`skipped.txt`に加え、`attempts.jsonl`へ試行ごとの開始要求・終了要求・採否を保存する。採否選択後のメモ入力は行わず、互換性のためログのnote欄は空文字とする。撮り直しごとに異なる記録ラベルを付ける。中断等で開始しかない行は採用済みとは扱わない。これらの時刻は操作ログであり、センサ時刻・反応時刻ではない。実ファイルとの対応は記録ラベルを用いて確認する。設定用/評価用の分割、校正のコピー、実測配置、バッテリー情報は別途台帳で保持する。

ファイル監査はmacOSでも標準Pythonだけで実行できる。

```bash
python3 scripts/experiments/audit_rc_popout_recordings.py \
  --root /path/to/recordings --output /path/to/inventory.json
```

MCAP、RAW、両metadataの存在・空ファイルを確認する。欠損または記録なしなら終了コード2。既存の出力は上書きしない。出力の予定方向はファイル名から読み取るが、実際のシーンラベルは`unknown`、同期と内容は`unchecked`とする。校正記録も対象に含まれ得るため、映像を確認して用途を付ける。

内容・同期の確認には既存の`multi-sensor-calibration inspect-bag`、LED同期・比較動画処理を使用する。例えば解析環境では次を使える。

```bash
bash scripts/experiments/run_rc_popout_auto_pipeline.sh --session /workspaces/record/SESSION
```

この既存パイプラインにはROS・Metavision等の解析環境が必要。今回追加したファイル監査はその代わりではない。RGB差分・EVS活動スコア・仮想ブレーキ要求・反応比較の解析器は今後追加する部分であり、本変更では実装していない。
